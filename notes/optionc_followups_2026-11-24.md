# Option C follow-ups: pre-stated specification (2026-11-24, committed before any follow-up score)

Two exploratory follow-ups to the Option C results (`optionc_results.md` on `main`), approved by the user on 2026-11-24. Neither changes a frozen rule, threshold, verdict or the reallocation; both are reported beside the frozen outputs as checks. This note is committed and pushed before either GPU job is submitted. Code: `scripts/optionc_followup/`; job script `pace/optionc_followup.sbatch`; outputs in `runs/optionc_fu/` of a fresh ICE checkout made from this commit.

## 1. Why the step-0 yes/no scores differ from Stage 1a's

**What is seen.** The rerun of the step-0 analysis (job 7295369, at `01cad81`) found Stage 1a's scoring runs and computed the promised `stage1a_agreement`: of the 3,867 step-0 yes/no scores under the aware, swapped and neutral prompts, 2,807 differ from Stage 1a's saved scores for Qwen3-8B after rounding to 1/64 nat (largest difference 2.0 nats) and 2,414 for Llama-3.1-8B (largest 1.125). The working guess is the GPU type: Stage 1a's Qwen scores were made on an A100-PCIE-40GB and its Llama scores on an A40 (job records of 7230581 and 7230582), Option C's on L40S GPUs (7245678, 7245679).

**What the records alone already show (read before this note).** Both jobs ran in the same environment (`.envs/serve`: torch 2.6.0, transformers 4.51.3; no file in its `site-packages` is newer than 2026-10-28), at code that differs only by the additions of `next_token_logprobs` and `last_only` in `wf/scoring/logodds.py` (with `last_only` off, as in the step-0 run, `next_token_logprobs` is the same computation as Stage 1a's `score_one_token_pair`: one unpadded forward pass of one prompt, bf16 weights, the last position's logits cast to float32 before the log-softmax). Stage 1a's records carry the pinned revision; the prompt builders, scorer loading and pinned revisions are unchanged between the two commits. The size of the disagreement matches a change of GPU type in the old stack: the project's reference comparison (Qwen yes/no, `rq1v_score` against `size_score_qwen3-8b`, 14,582 scores, 0.035 nats per score and 91% identical) splits into 12,869 scores where both runs used L40S GPUs (99.2% identical, 0.003 nats) and 1,713 from the one `rq1v_score` shard that ran on an A40 (28.6% identical, 0.273 nats, largest 2.25). Option C against Stage 1a for Qwen is 27.4% identical after rounding at 0.289 nats per score.

**What is still checked.** The records cannot rule out a difference in the prompts themselves (the two runs store hashes of different forms) and do not show causation. Two checks:

- **Prompts (CPU).** `prompt_dump.py` rebuilds the 3,867 prompts per model with each run's own code (this checkout for Option C; a copy of `wf/` at Stage 1a's commit `eeeb7dd` for Stage 1a), checks each against the hash that run stored with its score, and compares the messages and the token ids the scorer reads (each code's own tokenizer revision and template settings).
- **GPU diagnostic (about 0.5 GPU-hour).** `rescore_stage1a.py` runs Option C's own step-0 scoring path on the same 3,867 prompts on Stage 1a's GPU types: Qwen3-8B on an A100-40GB, Llama-3.1-8B on an A40. Each new score is compared with Stage 1a's record and with Option C's L40S record (share identical after rounding, mean absolute raw difference, largest rounded difference, acceptance flips).

**How it will be read.** GPU type is *established* as the cause for a model if its rescoring on Stage 1a's GPU type agrees with Stage 1a's records for at least 99% of scores after rounding with a mean absolute difference below 0.01 nats, while still differing from Option C's L40S records about as much as Stage 1a does. If the rescoring agrees with Option C's records instead, or with neither, GPU type is *not* the cause, and the cause lies in something the rescoring shares with Option C (code path, prompts or environment), which the prompt check then narrows. Anything in between is reported as measured, as *consistent with* the GPU type but not established.

## 2. The step-0 classification in plain text (about 0.7 GPU-hour)

**Why.** Option C's verifier ran in Qwen3's thinking-off template, which places an empty `<think></think>` block before the answer. The results note (section 10.3) says the step-0 classification "would very probably be unchanged in plain text" but did not compute it.

**What is scored.** Every job of the step-0 check for Qwen3-8B (Stage 1a's 134 step-0 states, every candidate, the aware, blind, swapped and neutral prompts, the yes/no and observation readouts: 10,378 scores), with Option C's own prompts (`verifier_messages`), rendered as plain text: no chat template, the Qwen pipeline audit's `plain_text` (section 7 of `qwen_effect_audit_pipeline.md`; the format behind Stage 1a's plain-text step-0 harm of 38.8 points against 71.6 with the block). The yes/no readout is the audit's `plain_pair` (" Yes" against " No" after one space). The observation readout is Option C's, at the position where the reply " Nothing happens." would begin after one space: with $P(\text{fail})$ the probability of that reply's first token,

$$
L_{\text{obs}} = \log\bigl(1 - P(\text{fail})\bigr) - \log P(\text{fail}).
$$

Scores are rounded to 1/64 nat and accepted above zero, as before. The job runs on an L40S, the GPU type of the logged with-block step-0 scores, and first rescores every job of the first 3 states with the block through Option C's own path, for comparison with the logged values (identical scores expected).

**What is compared.** `wf.optionc.step0_report`, the frozen analysis code, is applied unchanged to the plain-text scores: per readout the aware-minus-blind gap in accepting the 134 working first moves with its game-bootstrap interval, the gap state (collapse when the interval's upper end is below −30 points, no gap when the whole interval lies within ±10 points, otherwise unclear), the blind arm's competence (AUC at least 0.70, at most 95% of failures and at least 5% of successes accepted), and the classification in the design's order. The same code is run on the logged with-block scores and must reproduce the frozen classification and gaps. Reported beside them: acceptance of working first moves per arm, acceptance of failing candidates, the naming lift and any-task drop, and the first-token mass of the answers (" Yes" plus " No"; " Nothing" plus " You").

**How it will be read.** If the plain-text classification is "question-specific (supports the task-success reading)", the note's sentence is confirmed as computed. If it is any other label, the note reports the plain-text label as a format sensitivity of the step-0 check and names which readout moved (a yes/no gap that is no longer a collapse, or an observation readout that is no longer competent or shows a gap). In every case the frozen with-block classification, the reallocation decided on it and every loop verdict stand, because the procedure was frozen and the loop ran with the block. If the median first-token mass of " Yes" and " No" is below 0.5, the plain-text yes/no readout is off the model's usual path and is reported with that caveat.

**Expectation (stated before the score).** The yes/no readout collapses in plain text (the audit measured, with Stage 1a's identical aware prompt, 26.1% of first moves accepted against 97.8% task-blind, so a gap near −72 points); the observation readout keeps no gap; classification "question-specific", at about 70% confidence, the uncertainty being the plain-text observation readout, which has never been scored.
